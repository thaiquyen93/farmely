1. System Design
1.1 System Architecture
The system uses a modular monolith: a responsive React client accesses a Spring Boot REST API; PostgreSQL stores transactional and operational data. Domain services enforce business rules centrally. External adapters isolate weather, AI, simulated IoT and mock payment dependencies.
  

Figure 1 System architecture
Component

	Public Marketplace; role dashboards; responsive task execution forms. Chat polls every 5 seconds in the prototype.
	API and security
	Validate DTOs; authenticate JWT; enforce role and resource ownership; return consistent errors and pagination. Registration verification and password reset use the Email Service.
	Domain services
	Availability, reservation, contract, payment, cultivation, monitoring, communication and harvest rules.
	PostgreSQL
	Atomic bookings, foreign keys, immutable payment references, versioned processes and audit history.
	File storage
	Store image bytes outside business tables; retain metadata and authorized access references. Limit 5 MB per file and 10 images per task.
	Schedulers
	Expire holds, activate/end rental items, mark overdue tasks and evaluate environmental alerts. Jobs are idempotent.
	External adapters
	Mock payment only; simulated IoT every three hours; weather forecast API; LLM with approved knowledge retrieval; SMTP or email API for verification, password reset and critical notices.
	All server timestamps are stored as timezone-aware timestamps and displayed in Asia/Ho_Chi_Minh (GMT+7). Scheduling and policy decisions use server time. Clients cannot set prices, payment outcomes or effective contract status.
Security: Spring Security validates JWT and current account status. RBAC is combined with ownership checks: customers see their own contracts; experts see assigned plots; workers see assigned tasks and necessary plot information. Uploaded files require authentication and ownership checks. Passwords are stored as hashes. Secrets remain in server configuration.
Failure handling: reject invalid input before mutation; rollback failed database transactions; return 409 for unavailable intervals or stale updates. If weather is unavailable, show an unavailable indicator and do not automatically postpone watering. AI or weather failures must not block rental/payment transactions. Notifications are dispatched after commit with retry tracking.

2.1 Storage and naming conventions
PostgreSQL is the relational store. Proposed identifiers use BIGINT generated primary keys; foreign keys use the same type. Monetary values use NUMERIC(14,2), never floating point. Status values are constrained strings. Dates describe local farming dates; timestamps describe precise actions. Referenced financial and cultivation records are retained rather than physically deleted.
Contract is the aggregate header; contract_items represent individual plot rentals (the Rental concept). Every item has its own plot, variety, dates, mode, price snapshot and lifecycle. This supports BR05 and BR22 without forcing all plots to share a crop or period. There is no intermediate Order and no deposit entity.

	2.4 Integrity, availability and indexes
Availability is computed from effective plot_occupancies and publication status; plots do not store AVAILABLE/RENTED/RESERVED flags. Maintenance is an occupancy interval, initially open-ended until Admin records completion. BR23 therefore does not impose automatic release after four days. A booking interval uses [start, end) boundaries; date-only end dates are converted to the next local midnight so the final farming day is included.
Within a SERIALIZABLE transaction, lock candidate plots in ascending plot_id order, expire elapsed holds, validate all requested intervals and insert occupancy rows atomically. A conflicting item rolls back the whole reservation. A PostgreSQL exclusion constraint on plot_id + timestamp range for blocking rows is a second guard. Expired rows are explicitly released; time-dependent NOW() is not used in an index predicate.
Only one grace extension is allowed. Entering payment sets PAYMENT_PENDING and a deadline ten minutes after the original hold expiry. Callback handling locks the same reservation/occupancy rows, uses a unique provider reference and checks the effective deadline before confirming. Duplicate callbacks return the existing result; late success is logged for reconciliation/refund and cannot overwrite a newer booking.
Payment attempts may link to a pending contract created from the reservation; only a successful timely payment confirms it. Pending contracts do not independently block intervals. The confirmed contract retains the selected item and price snapshots; there is no Order table. Total paid is derived/reconciled from successful payment transactions. Refunds lock the source payment and enforce successful plus pending refunds ≤ amount actually paid.
Indexes: users(email); plots(land_id,listing_status); occupancies(plot_id,starts_at,ends_at); contract_items(contract_id,status,start_date,end_date); care_tasks(assigned_worker_id,scheduled_at,status); sensor_readings(plot_id,observed_at DESC); messages(conversation_id,message_id); notifications(recipient_id,read_at); audit_logs(entity_type,entity_id,occurred_at). Use unique generation keys for recurring jobs, callback references and task-generated diary entries.

3.6 Monitoring, Weather and Environmental Alerts
Rule: BR18. Customers view sensor data read-only. The simulator produces observations every three hours, while the alert evaluator uses observed episodes and recorded freshness. An alert exceeding 30 minutes can be acted on only when sufficient observations establish persistence. A single three-hour reading cannot prove continuous danger for 30 minutes; the demo must either supply a time-stamped alert test sequence or clearly show that persistence is unconfirmed.

3.8 Harvest, Contract Completion and Administration
Rules: BR20–BR24. Assigned field workers record harvest weight from an electronic scale and upload evidence; the customer accepts the result. 	3.10 Non-Functional Design
The design converts the SRS quality targets into measurable implementation constraints. Performance values are verified on the agreed demo environment with representative seed data; production-grade uptime and MTBF remain acceptance targets for the prototype baseline.
Quality area
	Design response / acceptance target
	Usability
	A returning Customer completes Reservation through Payment in under 5 minutes; show the server countdown and item-level validation without losing selections.
	Operating availability
	Target 99.0% availability during 06:00–23:00 GMT+7. Schedule maintenance during 02:00–05:00 and provide at least 24 hours advance notice.
	Reliability
	Target MTBF of 720 hours for reservation, payment and rental activation. Reservation/grace expiry jobs operate within 30 seconds and remain idempotent.
	Performance
	Payment callback to confirmation completes within 10 seconds. Chat polling makes a new message visible within one 5-second cycle.
	Capacity
	Support up to 50 active plots, 500 active rental items/contracts and 10,000 care tasks; indexed list/search queries return within 1 second in the target environment.
	Security
	bcrypt work factor 12 for passwords; JWT session policy; backend role plus ownership/assignment checks; externalized secrets; authenticated file access.
	Auditability
	Append actor, timestamp, action and affected entity for contract creation, payments/refunds, task changes, role changes and plot configuration.
	Maintainability
	Controller–Service–Repository separation; external adapters behind interfaces; schema changes managed by versioned Flyway or Liquibase migrations.
	External failure
	Weather, AI or Email failure returns a clear unavailable/pending state without losing core transactions. Payment unavailability preserves only the valid server-timed hold.
