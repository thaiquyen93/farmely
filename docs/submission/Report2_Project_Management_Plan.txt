2. Management Approach
2.1 Project Process
Agricultural Plot Rental and Cultivation Monitoring Platform is developed based on the Scrum framework - an Agile software development process. Therefore, it follows the three core Scrum values: transparency, inspection, and adaptation. Our team chose Scrum to develop this project for the following reasons:        
  

* Scrum is a management and process framework that solves complex problems while ensuring efficiency.
* Scrum itself is a simple framework that enables the most effective coordination among development team members when implementing products. This helps our team connect in the working process. At the same time, everyone knows each other's progress so they can work it out together as soon as possible if someone on the team has a problem.
* Because our product will be applied in a practical environment. Changing to match based on user requirements is frequent. Therefore, a flexible framework such as Scrum is suited for our team project.
* Our product built by Scrum is based on a series of short, iterative processes called sprints. It helps our team's project time to be utilised and optimised as much as possible.

For this project, each sprint spans 7 days and the duration of our product backlog is 8 weeks.
2.2 Quality Management
To maximise the project quality, our team will apply the following tactics to improve the project quality:
– Team policy:
* Define team policy: Working hours, meeting minutes, process,...

– Reviewing:
* Cross review between each member.

– Code convention:
* Define coding conventions for the Development Team to follow.

– Testing:
* Team members must do testing for their functions in the development environment before pushing it to production.
* Team members must do integration testing with other functions.
* Team members must record bugs and update them.

6. Configuration Management
6.1 Document Management
Keep the project context, SRS, SDS, management plan, tracking sheet, issues report, test evidence, and final release document in the shared project workspace. Name approved baselines by document version, maintain a change log with editor/date/summary, link decisions to the affected requirement or business rule, and review changes before publishing a new baseline. Preserve prior versions for traceability.
6.2 Source Code Management
Use GitHub with a protected main branch and short-lived feature branches. Link each pull request to a tracked task, require a peer review and successful build/tests, and use tagged demo baselines. Keep environment secrets out of the repository; use sample configuration and seeded mock data. Record database migrations with the code and prohibit direct schema edits in the shared database.
