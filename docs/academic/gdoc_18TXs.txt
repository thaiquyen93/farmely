II. Software Requirement Specification
1. Product Overview
The Farmely Urban Farming Management System is a new software platform that digitizes and replaces the traditional manual, fragmented processes for leasing agricultural plots, managing cultivation services, and tracking crop progress in owner-operated urban farms. The context diagram below illustrates the external entities and system interfaces for Release 1.0. The system is expected to evolve over several releases, ultimately connecting to physical IoT automated irrigation systems, real-time banking payment gateways, and agricultural e-commerce logistics services.

Main Operational Flow:

* System presents registration form.
* Visitor submits Full Name, Email, Phone Number, Password, and Confirm Password.
* System validates syntax and database uniqueness (V1.1 to V1.5).
* Server hashes the password with bcrypt (work factor 12).
* System inserts a new user record with role_id = 1 (ROLE_CUSTOMER) and status = 'ACTIVE'.

* If validation fails or duplicate credentials exist, display corresponding inline error messages (M1.1–M1.4) without clearing valid inputs.
Business Rules:
* Passwords are encrypted server-side using bcrypt (work factor 12) before database insertion.
* New accounts default to role_id = 1 (ROLE_CUSTOMER) and status = 'ACTIVE'.
* Successful registration redirects the user to /login.

* System confirms account status == 'ACTIVE'.

* System shows toast M2.3 and redirects based on user role:

   * ROLE_EXPERT -> /expert/dashboard
   * ROLE_STAFF -> /staff/dashboard
   * ROLE_ADMIN -> /admin/dashboard

* Accounts marked SUSPENDED or INACTIVE cannot authenticate.
* Role redirection: ROLE_CUSTOMER -> /customer/dashboard, ROLE_EXPERT -> /expert/dashboard, ROLE_STAFF -> /staff/dashboard, ROLE_ADMIN -> /admin/dashboard.

4. Non-Functional Requirements
4.1 External Interfaces
This section describes how the Farmely system communicates with its users and with external hardware or software elements.
User Interfaces
* Customer Web Application: A responsive web application built with ReactJS and TailwindCSS, accessible via modern browsers (Chrome, Firefox, Edge, Safari). The interface supports desktop viewports (1280 px and above) and mobile viewports (375 px and above). The default display language is Vietnamese.
* Agricultural Expert Dashboard: A web-based dashboard that allows Agricultural Experts to manage Crop and Variety catalogs, configure Standard Process Templates, handle pre-rental consultation requests, and communicate with Customers and Field Staff through in-app chat channels.
*  Field Staff Mobile View: A mobile-responsive web interface optimized for smartphone use at the farm. It displays the daily task list, task details with step-by-step instructions, a photo upload form for task evidence, and a chat channel to communicate with Agricultural Experts.
*  Administrator Dashboard: A web-based back-office panel that provides Administrators with tools for user account and role management, Plot and Land configuration, Rental and Reservation monitoring, Care Task dispatching, IoT alert configuration, and Audit Log review.
Hardware Interfaces
*  IoT Sensor Service (Mock): Simulated environmental sensors that provide Temperature (in degrees Celsius), Air Humidity (percentage), and Soil Moisture (percentage) readings every 3 hours for each Plot. In the prototype phase, all sensor data is generated programmatically. No physical IoT hardware is connected to the system.
* Smartphone Camera: Field Staff use the built-in camera on their smartphones to capture photographic evidence of task completion. Each photo must not exceed 5 MB in size, and a maximum of 10 photos may be attached per task.
Software Interfaces
* OpenWeatherMap API (HTTPS REST / JSON): Provides 3-to-5-day weather forecast data based on the geographic coordinates of each Plot. The system calls this API when the Plot Detail page loads and when the Customer Dashboard is refreshed.
* Payment Gateway – Mock (HTTPS REST / JSON): Simulates payment transactions with three possible statuses: Pending, Success, and Failed. It handles the full upfront rental payment (100 percent of the total, with no deposit required), Service Request fees, and Temporary Full-care Month Pass purchases.
* AI / LLM API with RAG (HTTPS REST / JSON): Powers the AI Chatbot assistant that answers agricultural questions from Customers. The service accepts user prompts along with contextual data retrieved from the Knowledge Document library managed by Agricultural Experts.
* PostgreSQL Database (TCP/IP, port 5432): The primary relational data store for all system entities, including Users, Plots, Rentals, Care Tasks, and Audit Logs. The database is administered through pgAdmin 4.
Communication Interfaces
* RESTful API (HTTPS, TLS 1.2 or higher): All communication between the client applications and the server uses JSON payloads over HTTPS RESTful endpoints. The backend is implemented with Java Spring Boot.
* Chat Polling (HTTP GET, 5-second interval): The in-app messaging feature between Customers and Agricultural Experts, as well as between Field Staff and Agricultural Experts, uses HTTP polling at a 5-second interval. Real-time WebSocket communication is deferred to a future release.
* Email Service (SMTP or third-party Email API): Used for sending account registration verification emails, password reset links, and critical system notifications such as Reservation expiry warnings and Payment confirmation receipts.
4.2 Quality Attributes
4.2.1 Usability
* Learnability: A new Customer with no prior training shall be able to browse the Marketplace, select a Plot, and complete a Reservation within 10 minutes on their first use.
* Task Efficiency: A returning Customer who has previously used the system shall be able to complete the entire flow from Reservation to Payment in under 5 minutes.
* Field Staff Onboarding: A newly onboarded Field Staff member shall be able to view assigned tasks, upload photographic evidence, and mark a task as Completed within 3 minutes of basic hands-on training.
* Error Guidance: All form validation errors shall be displayed inline next to the relevant input field, with context-specific messages that clearly indicate the problem and the corrective action required.
* Accessibility: The web application shall meet a minimum of WCAG 2.1 Level A compliance, including sufficient color contrast ratios (at least 4.5 to 1 for normal text), full keyboard navigability for all interactive elements, and appropriate ARIA labels for screen readers.
* Responsive Design: All Customer-facing pages shall render correctly on screen widths ranging from 375 pixels (mobile) to 2560 pixels (ultrawide desktop) without requiring horizontal scrolling or causing content overlap.
* Consistent User Interface: The application shall follow a unified design system using TailwindCSS utility classes and a shared component library to ensure visual consistency across all dashboards for every user role.
4.2.2 Reliability[d]
* Availability: The system shall maintain at least 99.0 percent uptime during operating hours (06:00 to 23:00, GMT+7, daily). Scheduled maintenance is permitted between 02:00 and 05:00 GMT+7, provided that users receive at least 24 hours of advance notification.
* Mean Time Between Failures (MTBF): The system shall achieve an MTBF of at least 720 hours (equivalent to 30 days) for all critical functions, including Reservation creation, Payment processing, and Rental activation.
* Mean Time To Repair (MTTR): In the event of a system failure during operating hours, the development and operations team shall restore normal service within a maximum of 2 hours.
*  Data Integrity for Concurrent Reservations: The system shall use PostgreSQL SERIALIZABLE isolation level combined with SELECT FOR UPDATE locking to prevent double-booking of the same Plot when multiple Customers attempt to create Reservations simultaneously.
* Reservation Expiry Accuracy: The automatic expiry of a Reservation (after 15 minutes) and the Grace Period extension (an additional 3 minutes while the payment status is Pending) shall execute with a timing tolerance of no more than 30 seconds.
*  Automatic Task Overdue Detection: Any Care Task that has not been marked as Completed by 23:59 GMT+7 on its scheduled date shall automatically transition to Overdue status. An alert notification shall be sent to the Administrator within 1 minute of the deadline.
*  IoT Data Validation: Sensor readings that fall outside the plausible environmental range (Temperature below 0 degrees Celsius or above 50 degrees Celsius) shall be automatically filtered out from dashboard displays and logged as data anomalies for Administrator review.
* Graceful Degradation for External Services: If the Weather API or the Payment Gateway becomes temporarily unavailable, the system shall display a user-friendly fallback message and continue operating all other features without data loss.
* Defect Rate: At the time of release, the number of critical defects (defined as complete data loss or a complete inability to use core features such as Rental creation or Payment processing) shall not exceed 0.5 defects per thousand lines of code. Any critical defect discovered after release shall be resolved within 48 hours.
4.2.3 Performance
Page Load Time: The Marketplace listing page and the Customer Dashboard shall fully load and become interactive within 3 seconds when accessed over a standard 4G mobile connection (approximately 10 Mbps).
API Response Time: At least 95 percent of all RESTful API requests shall return a complete response within 500 milliseconds under normal operating load. The maximum acceptable response time for any single API call is 2 seconds.
Payment Processing Time: The end-to-end payment flow, from the moment the Customer submits the payment request to the moment the system receives the gateway callback and activates the Rental, shall complete within 10 seconds.
Photo Upload Time: Uploading a single image file (up to 5 MB in size) shall complete within 5 seconds over a 4G connection. A visual progress indicator shall be displayed to the user during the upload.
Chat Message Delivery Latency: Messages sent through the in-app chat channels shall become visible to the recipient within 5 seconds, corresponding to one polling cycle.
Concurrent Users: The system shall support at least 100 concurrent active users across all roles (Customer, Agricultural Expert, Field Staff, Administrator) without any degradation in response time beyond the targets stated above.
Database Capacity: The system shall support up to 50 active Plots, 500 active Rental contracts, and 10,000 Care Task records simultaneously, with all list and search queries returning results in under 1 second.
IoT Data Throughput: The system shall handle the ingestion of simulated sensor readings for all 50 Plots at a 3-hour cycle (approximately 400 readings per day in total) without any processing backlog or data loss.
4.2.4 Security
Authentication: All users shall authenticate using their registered email address and password. Passwords shall be stored as salted hashes using the BCrypt algorithm with a cost factor of at least 10. User sessions shall be managed using JSON Web Tokens (JWT) with a configurable expiry period (default: 24 hours).
Role-Based Access Control: The system shall enforce role-based access control with four distinct roles: Customer, Agricultural Expert, Field Staff, and Administrator. Every API endpoint shall validate the requesting user's role before processing the request. Any unauthorized access attempt shall be rejected with an HTTP 403 Forbidden response.
Transport Layer Security: All communication between client applications and the server shall be encrypted using HTTPS with TLS version 1.2 or higher. Any incoming HTTP request shall be automatically redirected to HTTPS.
Input Validation and Attack Prevention: All user-submitted data shall be validated on the server side to prevent common web application attacks, including SQL Injection, Cross-Site Scripting (XSS), and Cross-Site Request Forgery (CSRF). Spring Security CSRF protection shall be enabled for all state-changing API operations.
 Data Access Isolation: Agricultural Experts shall only be able to access Plot data and consultations within their assigned scope. Field Staff shall only be able to view and update Tasks that have been assigned to them. Customers shall only be able to view their own Rental contracts, Payment transactions, Farm Diary entries, and Conversation threads.
Secure Password Recovery: The password reset process shall generate a unique, time-limited token (valid for 15 minutes) that is sent to the user's registered email address. The token shall become invalid after a single use or upon expiry.
Audit Trail: All critical system operations shall be recorded in the Audit Log. Logged operations include Rental creation, Payment transactions, Care Task status changes, User role modifications, and Plot configuration updates. Each log entry shall contain a timestamp, the identity of the actor, the action performed, and the affected entity.
File Upload Security: All uploaded image files shall be validated for permitted MIME types (JPEG and PNG only) and maximum file size (5 MB per file). The system shall reject files that do not meet these criteria and shall scan accepted files for embedded malicious content before storing them on the server.
4.2.5 Supportability and Maintainability
 Layered Code Architecture: The backend application shall follow a layered architecture pattern with clearly separated Controller, Service, and Repository layers to ensure maintainability and testability.
API Documentation: All RESTful API endpoints shall be documented using the Swagger / OpenAPI 3.0 specification. The interactive API documentation shall be accessible at the /api-docs endpoint in development and staging environments.
Structured Logging: The system shall implement structured logging using SLF4J with the Logback framework. Log messages shall be categorized by severity level (DEBUG, INFO, WARN, ERROR). All API errors shall be logged with the full request context and stack trace.
 Externalized Configuration: All environment-specific settings, including the database connection URL, third-party API keys, JWT signing secret, and email service credentials, shall be stored in external configuration files and shall never be hard-coded in the source code.
 Database Schema Migration: All database schema changes shall be managed through versioned migration scripts using Flyway or Liquibase to ensure that changes are reproducible, traceable, and consistent across all environments.

5.1 Business Rules
ID
	Rule Definition
	BR01
	Farm Ownership and Operation. The platform directly owns and operates the farm. Plots are planned and configured before being published for rental. The system does not support customers or external landowners listing land for rent (C2C).
	BR02
	Plot Unit. A Plot is the smallest unit of farmland managed and rented through the system. Each Plot has location, area, technical conditions, an availability calendar, a list of compatible varieties, and IoT data.
	BR03
	Approved Varieties and Compatibility. Customers must select a farm-approved variety compatible with the selected Plot. Customers may not independently bring varieties outside the approved catalog into the farm for cultivation.
	BR04
	Minimum Rental Duration. The rental duration must be equal to or longer than the expected growth duration of the selected variety plus its buffer time.
	BR05
	Contract Scope and Per-Plot Configuration. A contract may include one or more Plots selected by the customer. Each Plot in the contract is configured independently with a compatible variety, start date, end date, and cultivation mode. Plots in the same contract do not have to share the same variety, rental period, or cultivation mode.
	BR06
	Site Visits and Pre-rental Consultation. Guests and prospective customers may book a morning or afternoon farm visit by providing their full name and phone number. Online pre-rental consultation with an Agricultural Expert is optional and is not a prerequisite for booking a Plot.
	BR07
	Reservations and Schedule Conflicts. Only Plots published for rental and available throughout the selected period may be reserved. The rental period must not overlap a confirmed or active contract, an unexpired reservation, or the Plot’s soil-rest period.
	BR08
	Reservation Duration and Grace Period. Each reservation lasts 15 minutes. When the customer proceeds to payment, the reservation changes to pending payment and receives an additional 10-minute grace period. The grace period may be added only once per reservation.
	BR09
	Contract Payment. Customers must pay 100% of the total contract value upfront, including Plot rental charges and care fees applicable to the selected cultivation mode. No deposit is required.
	BR10
	Contract Cancellation and Refunds. Customers must submit a contract cancellation and refund request before the rental start date. The refund depends on the request time:
• At least 3 days before the start date: deduct 20% and refund 80% of the amount paid.
• Less than 3 days before the start date: deduct 50% and refund 50% of the amount paid.
• On or after the rental start date: no refund.
	BR11
	Cultivation Modes and Daily Care Packages. The system supports Self-growing, where customers care for the plants themselves, and Assisted-growing, where the farm provides comprehensive care. Self-growing customers may purchase delegated-care packages for a selected number of days when they cannot care for the plants themselves.
	BR11b
	Contract Renewal. Customers may renew a contract if the Plots to be renewed are available during the following period. Renewal must be completed at least 3 days before the contract end date. The current contract remains Active until the end of its rental term, then changes to Renewed after a successful renewal.
	BR12
	Standard Cultivation Process by Variety. Each variety has a standard cultivation process established by an Agricultural Expert. Assisted-growing Plots must fully follow this process; customer-specific process customization is not supported.
	BR12b
	Guidance for Self-growing Customers. Self-growing customers may consult the expert’s standard process or choose their own care approach. Any departure from the standard process must be approved or guided by an Agricultural Expert before implementation.
	BR14
	Care Task Assignment and Execution. Scheduled care tasks and tasks generated from service requests may only be assigned to Field Workers. Tasks not completed by 23:59 on their scheduled date automatically change to Overdue.
	BR15
	Task Completion Evidence. Field Workers must provide at least one actual photograph taken at the Plot before a task can be confirmed as Completed.
	BR17
	Farm Diary Synchronization. When a care task is completed, the system automatically records the performed work and its evidence in the farm diary for the Plot under the corresponding contract.
	BR18
	Environmental Data and Action Alerts. When an environmental alert persists for more than 30 minutes, the system responds according to the cultivation mode:
• Assisted-growing: automatically create an urgent care task during 08:00–17:00.
• Self-growing: notify the customer and offer an option to request rapid care.
When heavy rain is forecast or soil moisture reaches 80% or higher, the system automatically postpones the related watering tasks.
	BR19
	AI Assistant. The AI chatbot helps customers look up general cultivation knowledge, learn about plant diseases, and consult possible treatment methods.
	BR20
	Harvest Execution and Recording. Field Workers harvest the crops, weigh the yield using an electronic scale, take evidence photographs, and upload the results. Customers view and confirm acceptance of the harvest results.
	BR21
	Harvest Time and Location. Harvesting takes place at the farm at the end of the cultivation season.
	BR22
	Contract Completion. Each Plot rental ends on its own end date. Once a Plot rental ends, the system stops generating new cultivation tasks for that Plot but still permits outstanding requests to be handled. Other Plots in the same contract continue according to their respective rental periods. The contract changes to Completed only after all Plot rentals under it have ended.
	BR23
	Plot Release and Soil Rest. After a rental ends without renewal, the Plot changes to Maintenance for cleanup, tilling, and soil drying. The farm decides when soil rest is complete and the Plot can be reopened for rental.
	BR24
	Data Access Scope. Agricultural Experts may access operational data only for their assigned Plots. Field Workers may access only their assigned tasks and the related information needed to carry them out.
	BR25
	Communication Channels. The system supports customer–Agricultural Expert communication for consultation and Field Worker–Agricultural Expert communication for reporting and technical guidance. Customers do not directly assign work to or instruct Field Workers through the system.
	BR26
	Purpose of Cultivation Data. Cultivation data supports monitoring, traceability, and transparency of farm operations. It does not replace legal certification of food safety or organic production.
	BR27
	Service Catalog and Care Task Generation. The farm manages a catalog of per-visit care services and comprehensive delegated-care packages for a customer-selected number of days. After successful service payment, the system automatically creates the corresponding care tasks for assignment to Field Workers. Service prices follow the farm’s configured pricing policy.
